  Найденные проблемы

  1. payable считает отмену по снимку, а не на отчётную дату — 
  report.py:105-108.

  return sum((w.price for w in self.works if w.status_raw != "cancelled"), ...)

  Статус для отчёта уже вычисляется в status_on(on_date) (report.py:74-80), и
  таблица работ использует именно его (report.py:262), а итог «подлежит оплате»
  — сырой status_raw. Из-за этого на дату до отмены работы итог и строки
  расходятся.

  Пример: отчёт на 2026-10-01, W-13 отменена только 12.10. Код даст payable = 
  500 000, left = 200 000, при этом W-13 в таблице показана как запланированная
  и получает 100 000 аванса; сумма «осталось» по строкам — 300 000. Правильно на
  01.10: payable = 600 000, left = 300 000. Обратный случай: работа со
  status_raw = "done", но cancelled_at <= on_date попадёт в payable, хотя в
  таблице будет «отменена». На 10.11 W-13 уже отменена (12.10 < 10.11), поэтому
  этот отчёт не страдает.

  2. Ветка refunded игнорирует refunded_at — report.py:184-187.

  if (p.paid_at and p.paid_at <= on_date) or (p.created_at and p.created_at <=
  on_date):
      res.refunded += p.amount

  Поле refunded_at читается в report.py:155, но в расчёте не используется.
  Условие считает возврат состоявшимся по дате платежа/заведения, а не по дате
  возврата. Последствия:

  - отчёт на 2026-09-05: P-2 ушёл 02.09, вернулся 10.09. Код уже исключает 50
    000 из выплат и показывает возврат; фактически на 05.09 подрядчик эти деньги
    ещё держит. «Выплачено» будет 300 000 вместо 350 000, «осталось» завышено
    на 50 000;
  - если created_at <= on_date < paid_at, возврат покажется раньше, чем деньги
    вообще ушли.

  Правильно: считать возвратом только при refunded_at <= on_date; если возврата
  на дату ещё нет, но paid_at <= on_date — считать выплатой. На 10.11 P-2
  возвращён 10.09, поэтому цифры верные.

  3. Для paid-платежа без paid_at дата берётся из created_at — report.py:199 (и 
  та же логика в report.py:214).

  paid_on = p.paid_at or p.created_at

  DECISIONS §1 и README говорят, что платёж учитывается по paid_at. Fallback на
  created_at может включить платёж в отчёт до фактического перевода денег. В
  текущих данных у всех paid есть paid_at, на 10.11 не проявляется.

  4. Привязка платежа к работе не проверяет договор — report.py:204-205.

  if p.work_id and p.work_id in works:
      works[p.work_id].paid_direct += p.amount

  Если платёж по D-1 ссылается на работу из D-2, paid_total увеличится у D-1, а
  «выплачено» по работе — у D-2; итоги по работам перестанут сходиться с
  выплатами по договору. Если work_id вообще отсутствует в works, платёж
  останется только в paid_total: он не попадёт ни в одну строку работ и не
  попадёт в unallocated_advance, потому что там учитываются только платежи без
  work_id (report.py:210-216). В текущих данных все work_id корректны, но
  валидации ссылочной целостности нет. Аналогично молча пропускаются
  работы/платежи с неизвестным contract_id (report.py:174-181).

    при 3+ знаках копейки округлятся «к чётному», а не привычным ROUND_HALF_UP.

  - report.py:191 — queued без created_at молча не показывается.
  - report.py:253-255 — signed_at только печатается; договор, подписанный после
    отчётной даты, всё равно попадёт в отчёт. В данных оба договора подписаны
